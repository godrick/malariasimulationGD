# AGENTS.md

## Project purpose

`malariasimulationGD` is an R package for malaria transmission simulation with
mosquito genetics, genotype releases, metapopulation movement, explicit human
mobility, and both legacy and native mosquito backends.

Changes can affect epidemiological results, mosquito population dynamics,
release timing, reproducibility, runtime, and memory use. Treat model behaviour
and numerical output as part of the public interface.

## Repository layout

- `R/`: R package implementation.
- `src/`: compiled C++ implementation. The package currently uses C++14.
- `tests/testthat/`: unit, integration, regression, and end-to-end tests.
- `tests/performance/`: profiling and performance-related code.
- `test-scripts/`: runnable simulations, examples, calibration workflows, and
  generated outputs. This directory is excluded from package builds.
- `test-scripts/seven_node_example/`: compact metapopulation example.
- `test-scripts/Busia_landscape/`: larger landscape workflows that may be
  computationally expensive.
- `man/` and `NAMESPACE`: generated by roxygen2.
- `R/RcppExports.R` and `src/RcppExports.cpp`: generated Rcpp interfaces, when
  present.

## Before making changes

1. Read `DESCRIPTION`, the relevant implementation, and nearby tests.
2. Check `git status` and preserve all existing user changes.
3. Identify whether the change affects:
   - the human infection model;
   - mosquito population or genotype dynamics;
   - legacy versus native backends;
   - single-node versus metapopulation simulations;
   - human or mosquito movement;
   - release scheduling;
   - checkpoint/resume behaviour;
   - stochastic reproducibility;
   - generated documentation or Rcpp interfaces.
4. Prefer a focused change over broad refactoring.
5. Do not commit, push, create branches, or rewrite history unless explicitly
   requested.

## Scientific and behavioural guardrails

- Do not change scientific defaults, parameter interpretation, equations, units,
  timing conventions, or stochastic behaviour merely to make a test pass.
- If intended behaviour is unclear, inspect existing tests and documentation
  before choosing an interpretation.
- Preserve distinctions between mosquito backends:
  - `native_mosquito_backend = TRUE` selects the native count-based backend.
  - `individual_mosquitoes` also affects deterministic versus stochastic
    behaviour.
  - The legacy event-based individual-mosquito backend is not interchangeable
    with the native backend.
- When demonstrating the native count-based tau-leap workflow, explicitly use
  `native_mosquito_backend = TRUE` and set `individual_mosquitoes` deliberately.
- Explicit human mobility currently depends on the native metapopulation
  mosquito backend and its documented mixing and border-capture constraints.
  Do not silently relax these constraints.
- Preserve the distinction between temporary overnight human mobility and
  permanent migration. Human-carried state remains associated with the
  resident's home record unless the model is intentionally redesigned.
- Validate node ordering and dimensions for movement matrices, mixing matrices,
  contact surfaces, parameter lists, and output arrays.
- Movement probability matrices must retain their documented orientation and
  row-sum semantics.
- Treat release day, interval, count, sex, genotype, and node selection as
  scientifically meaningful inputs. Check indexing and off-by-one behaviour.
- Preserve checkpoint/resume equivalence where applicable.
- Use tolerances appropriate to floating-point or stochastic output. Do not
  require bit-for-bit equality unless deterministic equivalence is intended.

## Reproducibility

- Set an explicit RNG seed in stochastic tests and runnable examples.
- In comparisons between model arms, reset to the same seed when differences
  should arise from model configuration rather than RNG position.
- Avoid changing the number or ordering of random draws unless it is necessary
  for the requested behaviour.
- If a change intentionally alters the RNG stream or stochastic distribution,
  state that explicitly in the handoff.
- Tests should use small populations and short horizons unless scale is the
  behaviour under test.
- Do not rely on files or packages installed only in a developer's personal
  environment.
- Do not add machine-specific absolute paths.

## R implementation conventions

- Follow the style of the surrounding file; avoid unrelated formatting changes.
- Use explicit namespaces such as `stats::`, `utils::`, and `testthat::` where
  ambiguity is possible.
- Prefer integer literals such as `1L` for indices, counts, and timesteps when
  the distinction matters.
- Validate inputs near the public boundary and provide actionable error
  messages.
- Use `call. = FALSE` for user-facing validation errors when consistent with
  nearby code.
- Keep internal helpers unexported unless they are intentionally part of the
  package API.
- Add or update roxygen documentation for changes to exported functions,
  parameters, return values, or model semantics.
- Do not edit `NAMESPACE` or files in `man/` by hand. Regenerate them with
  roxygen2 when their sources change.
- Avoid adding new dependencies unless the benefit clearly justifies the
  installation and maintenance cost. Update `DESCRIPTION` when a dependency is
  genuinely required.

## C++ and Rcpp conventions

- Maintain compatibility with the C++14 setting in `src/Makevars` unless a
  toolchain change is explicitly requested.
- Preserve Rcpp registration and the package's existing R/C++ type boundaries.
- Carefully validate R-to-C++ indices, dimensions, ownership, and numeric types.
- Avoid copying large state objects in timestep loops without a demonstrated
  need.
- If an exported C++ signature changes, run:

  ```sh
  Rscript -e 'Rcpp::compileAttributes(".")'
  ```

  Review both generated interface files before keeping the result.

- Test both the R-facing behaviour and the native implementation affected by a
  C++ change.

## Performance work

- Establish a correctness baseline before optimizing.
- Measure the relevant workload before and after a performance change.
- Do not trade away scientific correctness, reproducibility, validation, or
  checkpoint compatibility for speed without explicit approval.
- Prefer vectorization, reduced allocation, and moving invariant work outside
  loops before introducing more complex parallel execution.
- Parallel workers must not write concurrently to the same output file.
- Parallel stochastic runs must use deliberate, reproducible, independent RNG
  streams.
- Report the scenario, replication count, core count, elapsed time, and any
  numerical differences when claiming a speedup.

## Testing strategy

Run the smallest relevant test first. A focused test file can be selected with:

```sh
Rscript -e 'testthat::test_local(".", filter = "native-mosquito-backend")'
```

Replace the filter with the affected test filename, excluding the `test-`
prefix and `.R` suffix.

For broader validation, run:

```sh
Rscript -e 'testthat::test_local(".")'
```

For package-level validation, run when proportionate to the change:

```sh
R CMD check --no-manual --no-build-vignettes .
```

Additional expectations:

- Add a regression test for every corrected bug when practical.
- Test invalid inputs as well as the successful path.
- For stochastic logic, test invariants or distributions rather than one
  fragile realization.
- For backend changes, cover the affected deterministic/stochastic and
  single-node/metapopulation combinations.
- For mobility changes, cover identity movement, nontrivial movement, returning
  travellers, and checkpoint/resume behaviour when relevant.
- For release changes, verify both the consumed schedule and resulting genotype
  counts.
- Do not weaken unrelated assertions to accommodate a change.

## Runnable examples and large workflows

Use the minimal or quick examples before running large landscape workflows:

```sh
Rscript test-scripts/run_minimal_release_example.R
Rscript test-scripts/seven_node_example/quick/00_run_quick.R
Rscript test-scripts/seven_node_example/quick/01_plot_quick.R
```

These scripts use an installed package. Ensure the installed package represents
the current working tree before treating their output as verification.
Prefer an isolated temporary R library when an installation is needed.

Do not run `test-scripts/install_local.R` without considering that it installs
packages into the user's default R library.

Do not run long calibration, careful-mode, Busia landscape, or large replicated
simulations unless they are necessary for the requested work. Start with a
small smoke-test configuration and report when full-scale validation was not
run.

## Generated files and outputs

Do not commit generated runtime artifacts unless explicitly requested,
including:

- simulation CSV files and plots;
- landscape output directories;
- `.Rhistory`, `.RData`, `.DS_Store`, and IDE state;
- compiled objects and shared libraries;
- package archives;
- `*.Rcheck` directories;
- profiling output;
- temporary calibration or checkpoint files.

Write experimental or diagnostic output to a temporary directory when
possible. Do not overwrite reference data or existing simulation output unless
the user explicitly asks for regeneration.

When documentation or Rcpp code generation is required, include only the
generated changes caused by the relevant source change.

## Dependency and environment safety

- Do not upgrade packages or modify the user's default R library without
  approval.
- Do not fetch large datasets or remote calibration artifacts unless requested.
- Do not assume optional packages from `Suggests` are installed; check first or
  skip with a clear explanation.
- Never include credentials, tokens, private paths, or unpublished data in
  source files, logs, or committed outputs.

## Completion criteria

Before reporting completion:

1. Review the diff for accidental formatting or generated-output changes.
2. Confirm the change is covered by an appropriate test or explain why a test
   was not practical.
3. Run the smallest relevant validation and broader checks in proportion to
   risk.
4. Summarize:
   - files changed;
   - model behaviour affected;
   - tests and simulations run;
   - checks not run and why;
   - expected numerical, stochastic, runtime, or compatibility effects.
